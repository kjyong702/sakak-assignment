# 구현 계획

이 문서가 구현의 기준이자 AI 코딩 도구에 주는 프롬프트다. 코드가 이 문서와 달라지면 문서를 먼저 고친다.

## 1. 요구사항 해석

| 안내서 요구 | 해석 |
|---|---|
| `GET /api/health/{patientId}` Mock API | 지정된 응답 형식을 그대로 돌려주는 FastAPI 엔드포인트. 환자별 JSON 파일에서 읽는다. 없는 환자는 404 |
| Ollama 12b 이하 모델, `/api/generate` 사용 | 호출은 이 엔드포인트 하나만 쓴다. tool calling용 `/api/chat`은 쓰지 않는다 |
| 건강 데이터를 바탕으로 질문에 답변 | 답변의 근거는 반드시 API 응답. LLM이 수치를 지어내지 못하게 판정을 코드가 먼저 한다 |
| LangGraph 권장 | 노드가 단계별로 분리된 워크플로 그래프. 조건 분기(검증 실패 시 재생성)에 그래프의 가치가 있다 |
| 모델 간 응답 비교 | 같은 질문 세트를 후보 모델 3개에 돌려 결과와 지연 시간을 표로 남긴다 |
| 동작 스크린샷 | 터미널 대화 화면과 API 문서 화면 |

## 3. 그래프 설계

```
START -> fetch_health -> select_metrics -> build_context -> generate_answer -> verify_answer -> END
                                                               ^                    |
                                                               +---- 재생성 (최대 1회) ----+
```

| 노드 | 하는 일 | LLM 호출 |
|---|---|---|
| `fetch_health` | Mock API를 호출해 건강 데이터를 상태에 넣는다. 같은 프로세스 안에서 ASGI로 부르므로 서버가 따로 필요 없고 라우터와 직렬화는 실제 요청과 같은 경로다 | 없음 |
| `select_metrics` | 질문에서 언급한 항목을 키워드 표로 고른다. 매칭이 없으면 전체 개요 | 없음 |
| `build_context` | 선택한 항목의 값, 단위, 참고 범위, **코드가 계산한 판정**을 텍스트로 렌더링 | 없음 |
| `generate_answer` | 시스템 프롬프트 + 컨텍스트 + 질문으로 `/api/generate` 호출 | 1회 |
| `verify_answer` | 세 가지를 검사한다. 답변의 수치가 컨텍스트(와 질문)에 있는가, 질문과 무관한 항목을 끼워 넣지 않았는가, 항목에 붙인 판정(또는 정해진 표현)이 컨텍스트의 판정과 같은가. 걸리면 사유를 붙여 한 번 재생성하고 그래도 걸리면 `verified: false`와 사유를 응답에 싣는다 | 없음 |

**판정을 코드가 하는 이유**: 7b급 모델은 "125가 120 미만인가" 같은 범위 비교를 자주 틀린다.
참고치 표(정상A, 정상B, 질환의심)를 파싱해 각 항목의 판정을 미리 붙여 주면 LLM은 설명만 하면 된다.
안내서의 예시 답변("혈압이 125/82로 약간 높은 편")도 참고치 기준 정상(B)에 해당하므로 이 방식과 맞다.

**LLM 호출을 한 번으로 제한하는 이유**: 로컬 7b 모델은 M3 16GB에서 한 번에 수 초에서 십수 초 걸린다.
항목 선택을 LLM에 맡기면 호출이 둘이 되어 응답이 느려지고 실패 지점도 는다. 키워드 표로 충분한 범위다.

## 4. 참고치 파싱

참고치는 자유 문자열이다. 자주 나오는 형태만 규칙으로 잡고 나머지는 "판정 없음"으로 둔다.

| 형태 | 예 | 처리 |
|---|---|---|
| `N미만`, `N이하`, `N이상`, `N초과` | `100미만`, `60이상` | 단일 경계 |
| `A-B`, `A~B` | `18.5-24.9`, `100-125` | 구간 |
| 성별 분기 `남: .. / 여: ..` | 헤모글로빈, yGPT, 허리둘레 | 환자 성별을 모르므로 남녀 판정이 같을 때만 확정하고 다르면 보류. 컨텍스트에는 두 판정을 모두 보여 준다 |
| 혈압 `수축기/이완기` | `120미만 이며/80미만`, `120-139 또는 /80-89` | 두 값을 따로 보되 '이며'는 둘 다, '또는'은 하나만 만족하면 해당 |
| 골다공증 `T-score -0.8` | `T-score -1 이상`, `-1~-2.5 초과`, `-2.5이하` | 숫자만 뽑아 수치 판정. '초과'가 붙은 구간은 열린 구간 |
| 요단백, 흉부 X선 | `음성`, `정상, 비활동성` | 문자열 규칙으로 판정 |
| 그 외 (키, 몸무게, 시력, 청력) | 참고 범위 없음 | 값만 제공, 판정 없음 |

판정 순서: 질환의심 -> 정상(B) -> 정상(A). 어느 것에도 안 걸리면 "판정 없음 (참고 범위 사이의 값)". 참고치 표에는
빈 구간이 있다 (LDL 140~159, 소수점 경계).

## 5. 프롬프트 설계

시스템 프롬프트에 넣는 규칙:

1. 주어진 검진 데이터만 근거로 답한다. 데이터에 없는 항목은 없다고 말한다
2. 수치는 단위와 함께 그대로 인용한다
3. 판정은 데이터에 붙은 판정 결과를 따른다. 스스로 범위를 다시 계산하지 않는다
4. 진단이 아니라 안내다. 주의 항목은 생활 습관 권고와 전문의 상담을 권한다
5. 한국어 존댓말, 3~5문장

컨텍스트는 항목마다 한 줄: `- 항목명: 값 단위 -> 판정 (참고치: 정상(A) .. / 정상(B) .. / 질환의심 ..)`.
전체 요약에서는 주의 항목과 핵심 항목만 줄로 주고 나머지 정상 항목은 각주로 묶는다.

규칙은 실제 모델 응답을 보고 여러 번 고쳤다. 최종 원문과 개정 경위는 `docs/prompt-iterations.md`에 있다.

## 6. 테스트 전략

Ollama 없이 전부 돈다. LLM은 `LLMClient` 인터페이스 뒤에 두고 테스트는 고정 답변을 돌려주는 가짜로 바꾼다.
Mock API 호출은 `httpx.ASGITransport`로 서버 없이 같은 코드 경로를 탄다.

- Mock API: 응답 형식, 없는 환자 404
- 참고치 파싱과 판정: 형태별 단위 테스트
- 항목 선택: 질문 문구별 선택 결과
- 그래프: 가짜 LLM으로 끝까지 실행, 검증 실패 시 재생성 분기
- Ollama 클라이언트: `httpx.MockTransport`로 요청 본문과 오류 처리

## 7. 실행 방식

```bash
ollama serve                      # 별도 터미널
ollama pull qwen2.5:7b
uv sync
uv run uvicorn app.main:app       # Mock API + POST /api/chat
uv run python -m app.chat         # 터미널 대화
```

## 8. 모델 비교

후보: qwen2.5:7b, llama3.1:8b, gemma3:4b. 같은 질문 세트(안내서 예시 2개 + 이상 수치 환자 질문)를 돌려
답변 원문, 지연 시간, 수치 정확성, 판정 준수, 한국어 자연스러움을 `docs/model-comparison.md`에 남긴다.
기본 모델은 비교 결과로 정한다.

## 9. 검토했다가 접은 대안

| 대안 | 접은 이유 |
|---|---|
| LangChain `ChatOllama` + tool calling으로 LLM이 API를 호출 | `/api/chat`을 쓰게 되어 안내서 지정 엔드포인트와 어긋난다. 도구 선택을 7b 모델에 맡길 이유도 없다 |
| 항목 선택을 LLM에 맡기기 | 호출 2회로 지연 증가. 키워드 표가 더 예측 가능하고 테스트 가능 |
| 판정을 LLM에 맡기기 | 범위 비교 오류가 잦다. 코드 판정이 정확하고 테스트 가능 |
| RAG(벡터 검색) | 데이터가 환자 1명의 검진 결과라 검색이 필요 없다. 전체를 컨텍스트에 넣는 편이 정확 |
