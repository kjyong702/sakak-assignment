# 개미수열 (Look and Say) 가운데 두 자리

n (3 < n < 100)이 주어지면 개미수열 n번째 항의 가운데 두 자리를 반환하는 함수이다.

### 1. 실행

```
cd look-and-say
uv sync
uv run pytest                      # 테스트 5건
uv run python -m look_and_say 8    # -> 21
```

- 풀이: look_and_say/naive.py
- 테스트: tests/test_look_and_say.py

### 2. 문제 이해

- 이전 항을 "몇 개의 무슨 숫자"로 읽은 것이 다음 항이다.
- 예시(n<=8)에 등장하는 숫자는 1, 2, 3뿐이다. 4가 나오려면 같은 숫자가 4개 연속해야 하는데 그런 경우는 생기지 않는 것으로 판단하였다.
  증명까지는 진행하지 못하였으나 이 판단에 따라 개수가 항상 한 자리라고 보고 개수와 숫자를 문자열로 이어 붙이는 방식을 택하였다.
- 첫 항이 1이므로 모든 항의 마지막 글자는 1이다.
- 항은 (개수, 숫자) 쌍으로만 구성되므로 길이는 항상 짝수다. 가운데 두 자리는 길이 L일 때 L/2번째와 L/2 + 1번째 글자이다 (1부터 셀 때)

### 3. 풀이 과정 (naive.py)

#### 접근 선택

한 번에 풀이가 떠오르기는 쉽지 않기에 가장 단순한 방법부터 접근하여 단서를 획득한다.
이 문제에서 가장 쉽게 떠올릴 수 있는 방식은 n번째 항이 어떤 값인지 실제로 구한 뒤 거기서 가운데 숫자를 꺼내는 것이다.
이 방법으로 정답이 나오는 것을 먼저 확인하고 어디까지 통하는지는 그다음에 보기로 하였다.

#### 다음 항을 만드는 과정

규칙을 코드로 옮기기 위해 표의 "1211 -> 111221"을 예로 단계별로 적으면 다음과 같다.

```
"1211" -> "111221"
1 을 본다: 세는 숫자 1, count 1
2 를 본다: 앞과 다르다 -> "11"을 적고, 세는 숫자 2, count 1
1 을 본다: 앞과 다르다 -> "12"를 적고, 세는 숫자 1, count 1
1 을 본다: 앞과 같다 -> count 2
끝: 남은 묶음 "21"을 적는다 -> "11" + "12" + "21" = "111221"
```

여기서 기억해야 하는 값이 셋(세는 숫자, 개수, 결과)이라는 것을 확인하고 그대로 변수로 두었다. 기록은 "직전과 다른 숫자를
만나는 순간"에 일어나며 마지막 묶음은 뒤에 다른 숫자가 오지 않아 루프 안에서는 기록되지 않는다는 점이 이 과정에서 드러났다.

#### 함수 분리와 테스트

문제를 "다음 항 만들기"와 "가운데 두 자리"로 나누어 각각 함수로 두었다. 안내서 표 7쌍과 예시 2개를 테스트로 먼저 작성하고 함수는 빈 상태로 시작하였다.
이후 경계값(n=4, 범위 밖 n=3/100 -> ValueError) 테스트를 추가하였고,
마지막 묶음 처리는 구현 후 회귀 테스트로 별도 추가하였다 ("2" -> "12", "111" -> "31", "1122" -> "2122")

#### 구현

- next_term: 문자열을 앞에서부터 한 글자씩 보면서 직전 숫자와 같으면 count를 늘리고 다르면 "count + 숫자"를 결과에 이어 붙인 뒤 count를 1로 초기화한다.
  마지막 묶음은 루프 종료 후 따로 추가한다.
- middle_two: "1"에서 시작해 next_term을 n-1번 적용한 뒤 가운데 두 글자를 반환한다.
  1부터 세는 L/2번째와 L/2+1번째는 0부터 세는 파이썬 인덱스로 L//2-1, L//2이다.

#### 한계 확인

구현이 예시를 통과한 뒤 n을 늘려 가며 항의 길이와 시간을 재었다.
그 결과가 4절이고 이 풀이가 문제가 요구하는 범위 전체를 처리하지 못한다는 것을 여기서 확인하였다. 그 뒤에 검토한 방향은 5절에 적었다.

### 4. 복잡도

next_term 1회는 O(항 길이)이다. 전체는 1항부터 n항까지 길이의 합이므로 길이가 어떻게 커지는지 측정하였다.

| n   | 항의 길이  | 10단계 전 대비 | 누적 시간 |
| --- | ---------- | -------------- | --------- |
| 10  | 20         |                | 0.00초    |
| 20  | 302        | 15.1배         | 0.00초    |
| 30  | 4,462      | 14.8배         | 0.00초    |
| 40  | 63,138     | 14.2배         | 0.01초    |
| 50  | 894,810    | 14.2배         | 0.18초    |
| 60  | 12,680,852 | 14.2배         | 2.58초    |

- 10단계마다 약 14배 (한 단계에 약 1.3배)로 비율이 일정하므로 길이는 지수 함수이다. 시간 O(1.3^n), 공간 O(1.3^n), 가운데 추출은 O(1)
- n=99까지 가면 약 4 x 10^11 자리 (약 400GB)라 메모리에 올릴 수 없다. 실제로 동작하는 범위는 n=80 근처까지이다 (16GB 기준)

### 5. 보완할 점

- n=99까지 처리하려면 항 전체를 만들지 않고 가운데 위치만 구하는 방법이 필요하다. 풀이 방향은 생각했지만 구현하지는 못하였다.
  (next_term이 입력을 앞에서부터 한 번만 읽고 출력도 순서대로 만들기 때문에 이전 항을 통째로 들고 있지 않아도 될 것 같지만 시간 복잡도는 그대로)
- 정수가 아닌 입력과 명령줄 인자 오류에 대한 처리는 넣지 않았다.

### 6. 소감

문제를 처음 읽었을 때는 규칙이 바로 들어오지 않아 표를 여러 번 읽어야 했다.
풀이가 떠오르지 않을 때는 늘 하던 대로 가장 기본적인 방법, 비효율적이더라도 구현이 확실한 방법부터 잡았다.
그 방법으로도 풀리지 않으면 다른 영역의 문제이거나 그 방법 자체가 답이라는 뜻이고 풀린다면 거기서 개선할 곳이 보이기 때문이다.

알고리즘 문제는 입출력 예시에 힌트와 규칙성이 있기 마련이라고 생각한다.
이번에도 예시에서 등장하는 숫자가 1, 2, 3뿐이라는 점과 마지막 글자가 항상 1이라는 점을 먼저 찾았고 그것이 풀이의 출발점이 되었다.
규칙성이 보이지 않는 문제라면 풀이 아이디어보다 구현 자체를 묻는 문제일 가능성이 높다고 본다.

복잡도는 스스로 떠올리지 못한 부분이다. 검색을 통해 항의 길이가 지수적으로 커진다는 힌트를 얻은 뒤에야 n을 늘려 가며 직접 길이와
시간을 재서 그 비율이 실제로 일정하다는 것을 확인하였고 이 풀이가 문제가 요구하는 범위 전체를 처리하지 못한다는 것을 알게 되었다.
